# Chief Hub: инструкции для Claude

Универсальная панель шеф-бариста для сети спешелти-кофеен (3+ точек). React + TypeScript + Vite, PWA, публикация через GitHub Pages. Реалии конкретной компании не использовать: всё общее и настраиваемое.

Сайт: https://htongrad.github.io/chief-hub/
Репозиторий: github.com/htongrad/chief-hub (ветка main).

## Кто пользователь и как он работает
- Не программист. Работает с телефона. Объяснять простыми словами, без жаргона.
- Сам использует инструмент как шеф-бариста нулевого дня и просит менять структуру панели по мере работы. Его замечания из реальной работы важнее теоретических идей.
- Все шаги вне кода (GitHub, настройки, проверка сайта) давать короткой нумерованной инструкцией под телефон.

## Экономия лимитов
- Отвечать коротко. Править только нужные файлы. Не пересоздавать проект и архив без просьбы.
- Если задачу можно решить одной правкой, не предлагать большой план.
- Не читать весь репозиторий: структура описана ниже и в docs/ARCHITECTURE.md.
- Перед нетривиальной задачей назвать подходящую модель и почему: Haiku (тексты, мелкие правки, цвета), Sonnet (новые разделы, баги, основная работа), Opus (облако, роли доступа, смена структуры данных, сложные ошибки). Если задача проще текущей модели, предложить переключиться.

## Структура кода
- `src/modules/` — разделы в порядке меню: Overview, Quality, Team, Inventory, Metrics, Equipment, Rounds, Report, Playbook, Settings. Порядок повторяет `docs/JOB_DESCRIPTION.md`: это основа панели.
- `src/modules/TheoryCost.tsx` — не раздел меню, а две карточки «Показателей» (себестоимость по ТТК по дням, факт против ТТК). Такие вспомогательные компоненты лежат рядом с разделом, который их подключает, и в реестр разделов не попадают.
- `src/config.ts` — реестр разделов, навыки команды, должности, чек-лист обхода, план «Путь шефа».
- `src/store.tsx` — хранилище (localStorage, адаптер для будущего облака), миграция данных `migrate()` и расчёты (нормы эспрессо, ТО, аттестации, сигналы, недельный отчёт, периоды показателей, средняя цена позиции, себестоимость по инвентаризации и по ТТК, сборка списаний). Расчёты показателей и себестоимости искать здесь, а не в `Metrics.tsx` и `Inventory.tsx`.
- `src/backup.ts` — копия на Google Диск: листы таблицы (`buildSheets`), автосохранение и код скрипта Apps Script. Новый раздел или поле данных — добавить и сюда, в `buildSheets`; сам скрипт при этом менять не нужно.
- `src/types.ts` — описание данных. `src/seed.ts` — демо-данные.
- `src/styles.css` — цвета и размеры (есть тёмная тема).
- `docs/PRODUCT.md`, `docs/ARCHITECTURE.md`, `docs/ROADMAP.md`, `README.md` — документация, обновлять при изменении продукта.

## Правила работы с кодом
- Новое поле данных: добавить в `types.ts` и `seed.ts`. При несовместимой смене формы поднять `version` и написать миграцию в `store.tsx`. Необязательное новое поле (например, сумма в приходе) или новый список с пустым значением по умолчанию версию не меняют: достаточно значения по умолчанию в `migrate()`, и старые данные открываются как есть.
- Не удалять `package-lock.json`, если он появится: без него сборка на GitHub падает на шаге кэша. В workflow кэш сейчас не используется.
- Расчёты держать в `store.tsx`, не в разметке.
- Каждое поле, которое пользователь заполняет в форме, должно быть видно в панели и на нужном листе копии на Диске (`buildSheets` в `backup.ts`). Проверять это при добавлении поля и сообщать пользователю, где оно видно.
- Перед тем как сказать «готово», проверить сборку: `npm install` и `npm run build`. Если запустить не удалось (в этой среде npm может быть закрыт), сказать об этом прямо и опираться на сборку на GitHub.
- Если демо-данных для проверки расчёта не хватает (например, нет двух инвентаризаций с ценами), собрать тестовые данные прямо в скрипте во временной папке сессии, не внутри репозитория. Проверять границы периодов, пустые данные и миграцию старых данных.
- Перед правкой прочитать тот файл, который меняется.

## Как идёт публикация
1. Правки вносятся отдельной веткой `claude/...` (через Claude Code в облаке), затем открывается PR в `main`, и пользователь нажимает Merge. Прямых правок в `main` не делать.
2. Сайт обновляется только после слияния PR: каждый push в `main` запускает задачу *Deploy to GitHub Pages* (вкладка Actions). Пока PR открыт, сайт старый.
3. Перед тем как сказать «сайт обновлён», проверить состояние PR и задачу в Actions (`gh api repos/htongrad/chief-hub/pulls/N`), а не гадать.
4. Через 1–3 минуты после слияния сайт обновляется. Если задача упала, открыть её в Actions и прислать в чат первые строки ошибки шага. Лог целиком в чате не нужен.
5. В чат сообщать, что проверить на телефоне: какой раздел изменился и где это видно. Если на телефоне старая версия, попросить закрыть приложение с ярлыка полностью и открыть снова.
6. В этой среде `gh pr create` не работает (GraphQL закрыт). PR открывать через `gh api repos/htongrad/chief-hub/pulls -f title=... -f head=... -f base=main -F body=@файл`. После первой отправки ветки делать `git push -u`, иначе стоп-хук пишет, что ветка не связана с удалённой.
7. В начале задачи проверить через `gh api repos/htongrad/chief-hub/pulls/N`, слиты ли прежние запросы, и строить ветку от свежего `main`. Если задача зависит от неслитого запроса, сказать об этом и указать порядок слияния.

## Договорённости по продукту
Договорённости по Складу, выручке, ценам и себестоимости описаны в `docs/PRODUCT.md` (разделы «Склад» и «Показатели»). Менять их только после согласия пользователя. Коротко: все цены и себестоимость с НДС (сумма по накладной с НДС, отдельного поля НДС нет); основная себестоимость считается по инвентаризации от выручки бара; продажи для ТТК пока вносятся вручную в «Расход за день».

## Что делать с замечаниями пользователя
- Записывать замечания из реальной работы в `docs/ROADMAP.md` в нужную версию или в «Идеи без срока».
- Если замечание меняет структуру (новый раздел, новое поле, другой план), сначала коротко предложить вариант и дождаться «да», потом делать.
- Если пользователь отменяет ранее согласованное (например, поле НДС в приходе), следовать последнему решению и убрать это из кода, плана и документации.
- Мелкие правки (тексты, порядок пунктов, цвета) делать сразу.
- Переименование термина (раздел, кнопка, пункт плана, подсказка в меню): менять во всём проекте, включая `config.ts`, `README.md` и `docs/`, и сказать пользователю, какие места изменены.
